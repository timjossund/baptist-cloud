# 0001. Audio app stack and architecture

**Date**: 2026-10-18
**Status**: Proposed

## Summary

The listening app is built with Expo (a set of tools on top of React Native) and TypeScript. Screens and links use Expo Router, sermons play through react-native-track-player so audio keeps going with the phone locked, and the sign in token lives in the phone's secure storage (iOS Keychain, Android Keystore). Builds for testers and the stores go through EAS Build, Expo's build service, and over the air updates through EAS Update are chosen now but wired at store release. The app is one small project in `audio-app/`, separate from the Laravel site, talking to it only through the `/api/v1` API.

## Requirements

**User stories**:
- As the app developer, I want a scaffold that already runs on both platforms with the audio and token libraries in place, so slice 1 starts on product work instead of build fixes.
- As a listener, I want sermons to keep playing with lock screen controls when my phone is locked (delivered in feature 5, enabled by this stack).

**Acceptance criteria** (for the scaffold this feature ships):
- **AC-1**: `audio-app/` is an Expo SDK 58 project (React Native 0.88, Hermes, New Architecture on, TypeScript strict, typed routes and React Compiler on) that installs with `npm install` and keeps its own `package-lock.json`, apart from the Laravel `package.json`. `audio-app/.nvmrc` pins Node 24.
- **AC-2**: A development build boots on an iOS simulator (`npx expo run:ios`) and on an Android emulator (`npx expo run:android`) and shows a home screen rendered through Expo Router.
- **AC-3**: The development build includes `react-native-track-player` pinned to an exact version (4.1.2) and `expo-secure-store`. `package.json` `main` is `index.ts`, which registers the playback service before loading `expo-router/entry`. iOS declares background mode `audio`; Android declares `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PLAYBACK`, and `POST_NOTIFICATIONS`. On launch the home screen calls `TrackPlayer.setupPlayer()` and shows whether the player is ready, proving the native module loads on both platforms.
- **AC-4**: `APP_VARIANT` picks the build variant in `app.config.ts`. `production` (the default) uses app id `cloud.baptist.audio` and name "Baptist Cloud"; `development` uses `cloud.baptist.audio.dev` and "Baptist Cloud Dev", so a dev build installs beside a store or TestFlight build. The deep link scheme is `baptistcloud` (`baptistcloud-dev` for development). Portrait only, light and dark follow the system, Android draws edge to edge.
- **AC-5**: The API base URL is read from `EXPO_PUBLIC_API_URL`; `audio-app/.env.example` documents it and real `.env` files are ignored by `audio-app/.gitignore`. Plain `http` is allowed only in the development variant (iOS App Transport Security local exception, Android cleartext traffic); production allows only `https`.
- **AC-6**: The native `ios/` and `android/` folders are generated by `npx expo prebuild` and ignored by `audio-app/.gitignore`; `app.config.ts` is the only place native settings change.
- **AC-7**: Android `allowBackup` is off, so a phone restored from backup never receives a stored token it cannot decrypt.

## Decision

**Chosen option**: Option 1: Expo with continuous native generation

Build the app on Expo SDK 58 with prebuild, Expo Router, react-native-track-player, expo-secure-store, development builds, and EAS Build, with EAS Update as the planned update path.

## Proposed stack

| Layer | Choice | Reason |
|---|---|---|
| Language | TypeScript, strict mode | Catches API shape mistakes at build time; Expo's default template already uses it. |
| Framework | Expo SDK 58 (React Native 0.88, React 19.3, New Architecture) | Expo manages the native projects and upgrades, so a small team spends its time on the app, not Xcode and Gradle files. |
| Project setup | Continuous native generation (`npx expo prebuild`), `ios/` and `android/` not committed | Native settings live in `app.config.ts` and config plugins, so SDK upgrades regenerate cleanly. |
| Dev runtime | `expo-dev-client` development builds, not Expo Go | Track player is native code Expo Go cannot load. |
| Navigation | Expo Router (file based routes under `src/app/`) | Typed routes and deep links (for example a sermon link from the website) come built in. |
| Background audio | `react-native-track-player` 4.1.2, exact pin, plus `patches/react-native-track-player+4.1.2.patch` (applied by `patch-package` on `npm install`). The patch fixes three Android problems on React Native 0.88 with the New Architecture: two `Arguments.fromBundle` nullability compile errors, `@ReactMethod` functions that returned a coroutine `Job` instead of nothing, and the playback service reading the removed `ReactNativeHost` instead of `reactContext`. iOS needs no patch. | Built for podcast style apps: background play, lock screen and notification controls, playback speed, remote commands, and a path to CarPlay and Android Auto (deferred). |
| Secure token storage | `expo-secure-store`, `keychainAccessible: AFTER_FIRST_UNLOCK` | First party wrapper over iOS Keychain and Android Keystore, enough for the one bearer token from `POST /api/v1/auth/token`; readable while the phone is locked so background playback can still call the API. |
| Build variants | `APP_VARIANT` = `development` or `production` (default) in `app.config.ts` | Separate app id, name, scheme, and cleartext rules per variant; EAS profiles set it later. |
| Native build settings | `expo-build-properties` for Android cleartext in development; `ios.infoPlist` for background mode and the local network exception | Keeps every native setting in config, so prebuild stays repeatable. |
| Toolchain | Node 24 (`.nvmrc`), Xcode 27, JDK from Android Studio (`JAVA_HOME`), Android SDK 37 | What SDK 58 builds with on this Mac; recorded so another machine matches. |
| API access | Plain `fetch` against `EXPO_PUBLIC_API_URL` | The API is small JSON with `{ message, code }` errors; feature 3 decides the client layer and caching. |
| Config | `app.config.ts` plus `EXPO_PUBLIC_API_URL` from `audio-app/.env` (local) and EAS environment variables (builds) | One source for native settings and the API URL per environment. |
| Package manager | npm, own `package-lock.json` in `audio-app/` | Already installed and used by the Laravel side; no workspace tooling needed for two unrelated apps. |
| Builds and store submission | EAS Build and EAS Submit; `npx expo run:*` and `eas build --local` locally | EAS handles signing certificates and keystores; the free plan covers a small team's build count. |
| Over the air updates | EAS Update, wired at store release (feature 9) | Lets JavaScript fixes ship without store review once live; the runtime version will follow the app version. |
| Minimum OS | Expo SDK 58 defaults | No reason to support older phones than the SDK does; revisit if store analytics show a need. |

**Project layout** (inside `audio-app/`):

```
app.config.ts        native settings, plugins, variants, app id, scheme
index.ts             package main: registers the playback service, then imports expo-router/entry
src/app/             Expo Router screens (_layout.tsx, index.tsx)
src/audio/service.ts track player playback service (remote play, pause, seek)
.env.example         EXPO_PUBLIC_API_URL, APP_VARIANT
.nvmrc               Node version
.gitignore           ios/, android/, .env, .expo/
```

**Development API URL**: the iOS simulator can use `http://baptist-cloud.test` (allowed by the development variant's local exception). The Android emulator cannot resolve `.test` names, and `http://10.0.2.2` reaches the Mac but not this site, because Herd picks the site by host name. Use `herd share` (an https tunnel) as Android's `EXPO_PUBLIC_API_URL`. Feature 5 is the first feature that calls the API and writes down the exact local recipe.

## Consequences

**Positive**:
- Native folders are generated, so upgrading Expo means bumping versions and running prebuild again, not merging Xcode and Gradle diffs.
- Proving track player and secure store in the scaffold surfaces native build problems now, not in the middle of slice 1.
- Deep links from the website to a sermon screen cost little later.

**Negative / tradeoffs**:
- Expo Go cannot run the app; every native dependency change needs a new development build (minutes on a Mac).
- react-native-track-player is a community library; 4.1.2 already needs a local patch to build and start on Android with SDK 58 and the New Architecture, and a past 4.1 release broke on a newer Expo SDK too. If it breaks on an upgrade, the fallback is `expo-audio` with its lock screen support.
- EAS ties store builds to an Expo account; the free plan caps builds each month and queues slowly (check the current limits when feature 9 starts). `eas build --local` is the escape hatch.
- Over the air updates cannot change native code. Any native dependency change (for example a track player upgrade) needs a new app version and store build.
- The iOS Keychain keeps the token after the app is deleted and reinstalled; feature 3 decides how a fresh install clears it.
- Native settings must go through config plugins; a hand edit in `ios/` or `android/` is lost on the next prebuild.

**Neutral**:
- The repo now has two npm projects; run npm commands from `audio-app/` for the app.
- Running on devices needs Xcode, CocoaPods, the Android SDK, and a JDK (Android Studio's bundled one works via `JAVA_HOME`).
