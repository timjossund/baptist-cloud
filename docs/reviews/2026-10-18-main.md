## Summary
This adds the first JSON API: Sanctum tokens, a sign in route with three throttles, `/me`, sign out, an idle expiry, token revocation on password change, reset, and account deletion, and a single error layer that turns every `/api/` error into `{ message, code }`. The code follows the spec closely and I could not find a path that leaks a token, skips the password check, or lets the website session reach the API. The middleware order fix in `bootstrap/app.php` is correct. What is left is small: a few behaviors worth knowing about and two thin spots in the tests.

## Minor
### 🟡 Anyone can lock a person out of the app for 15 minutes, `app/Http/Controllers/Api/TokenController.php:39`
**Problem**: The `email` limit counts failures for one email from any IP. Someone who knows your email (it is not secret) can send 10 wrong passwords and you get `429 too_many_attempts` on the app for up to 15 minutes, even though your password is right.
**Why it matters**: The spec chose this as a backstop against faked IPs, but its Consequences section does not list the lockout as a tradeoff. It is annoying, not dangerous, and the website login has the same shape.
**Suggested fix**: Add one line to the spec's Negative / tradeoffs so the choice is on record. No code change needed unless the lockout shows up in real use.

### 🟡 No test proves the unknown email path really runs a hash check, `tests/Feature/Api/TokenAuthTest.php:107`
**Problem**: The test checks that a wrong email and a wrong password give the same body. Nothing checks that the dummy hash branch (`TokenController.php:61`) runs, so someone could delete that line and every test would still pass.
**Why it matters**: AC-2 promises equal timing so that the response time does not reveal which emails have accounts. This is security relevant and currently unguarded.
**Suggested fix**: Spy on `Hash::check` (or the hasher) for the unknown email case and assert it is called once.

### 🟡 The dummy hash cost is fixed at 12, `app/Http/Controllers/Api/TokenController.php:25`
**Problem**: Real passwords are hashed with `BCRYPT_ROUNDS` (12 in `.env.example`, 4 in tests). The dummy hash is cost 12 forever. If production ever sets a different rounds value, a wrong email and a wrong password stop taking the same time.
**Why it matters**: It quietly weakens the timing protection in AC-2 later, with nothing to warn you.
**Suggested fix**: Build the dummy hash once from `Hash::make` with the app's current settings (cache it in a static), or add a comment next to the constant saying it must track `BCRYPT_ROUNDS`.

## Nits
- ⚪ `app/Http/Controllers/Api/TokenController.php:42`, the throttle check and the later `hit` calls are separate steps, so a burst of parallel requests can slip a few extra attempts past a limit. Fine at this scale; the three limits overlap anyway.
- ⚪ `app/Http/Controllers/Api/TokenController.php:46`, a blocked request writes up to three log lines. During an attack that is a lot of log noise. The spec asks for it, so just be aware.
- ⚪ `app/Exceptions/ApiException.php:70`, Laravel does not report a thrown `HttpException` by default, so an `abort(500)` in future API code produces the fixed JSON but may leave no log entry. Plain exceptions are logged as normal. Worth remembering when writing feature 21.
- ⚪ `database/migrations/2026_10_18_010615_create_personal_access_tokens_table.php:19`, `abilities` is `text` (Sanctum's own migration) while the spec's data table says json. Harmless; update the spec wording.
- ⚪ `app/Http/Resources/Api/UserResource.php:30`, `avatar_url` assumes `User::avatar` always returns a relative path. If avatars ever move to a disk that returns full URLs, this will double the host.

## Strengths
- Every sign in outcome in AC-1 to AC-4 is in the right order: validate, throttle, hash check, then the verified check, with blocked requests adding no hits and success clearing only the two counts the spec names.
- The idle rule correctly keeps Sanctum's `$isValid` and has boundary tests at exactly 90 days and one second past, and the prune keys on last use, not age.
- The priority list fix is correct and has two regression tests proving 403 refusals do not use up the per user limit.
- The error layer returns fixed messages only, passes `Retry-After` and `Allow` through, leaves `HttpResponseException` alone, and has a test that `APP_DEBUG` never leaks detail.
- Tests use real `createToken()` tokens and cover token revocation for password change, reset, and deletion, plus other users' tokens being untouched.

## Test coverage
43 Pest tests tagged by AC cover every acceptance criterion, including the edges (case changes in the email, two limits blocking at once, wrong secret on a real token id, non bearer headers, sessions ignored, no cookies). The gaps are the timing path above and one small item: nothing asserts the `DELETE /auth/token` route itself is rate limited by `api-user` (it is, in `routes/api.php:14`); that is low risk.
