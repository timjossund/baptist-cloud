## Summary
Adds a Member plan, a plan tier rule on `User`, a per user monthly view meter (`ContentMeter`, `content_views`), an article preview paywall, and signed sermon audio links, with billing validation that takes the Stripe price only from config. The implementation follows the spec closely and I found no paywall leak through the views, no price tampering path, and no authorization gap. The only real concern is that the article preview is bounded by block count, not size, so a post with few blank lines gets shown almost whole.

## Minor
### 🟡 Article preview is bounded by block count, not length, `app/Http/Controllers/PostController.php:115`
**Problem**: The preview takes the first 3 blocks split on blank lines. A post written as one long paragraph (or with single newlines between lines, or a post that is a single big list or code block) is one block, so the "preview" is the entire article.
**Why it matters**: AC-9 and AC-13 intend that a paywalled page does not carry the full body. For such posts the paywall is bypassed entirely, and the author can't tell. The spec accepts a block being cut early, not a block being too large.
**Suggested fix**: Also cap the preview by length (for example truncate the raw Markdown to a few hundred words or characters at a word boundary after taking the 3 blocks), and add a test with a single long block.

### 🟡 No test for an oversized or single block preview, `tests/Feature/MeteredAccessTest.php:97`
**Problem**: The short post test covers the opposite case (one short block). Nothing asserts that a long single block is not fully exposed on the paywall.
**Why it matters**: This is the leak path above; it is security relevant and currently unguarded.
**Suggested fix**: Add the test together with the length cap.

### 🟡 Unknown price warning fires on every request, `app/Models/User.php:99`
**Problem**: `Log::warning` runs once per request per affected user (the memoization is per model instance). A subscriber on an unlisted price, for example a forgotten legacy price, writes a warning on every page load.
**Why it matters**: Log noise can bury the signal, and it is the only alert for the main rollout risk (AC-4). Spec mandated, so low severity.
**Suggested fix**: Optionally throttle with a short `Cache::add` key per price so it logs once per hour.

## Strengths
- Price IDs only ever come from config and `plan` is allowlisted; a test proves a forged `price` field is ignored and Stripe is never reached on bad input.
- The paywall path never assigns the full body or an audio URL to the view, and tests assert absence from the HTML (`<audio`, the audio path, the tail of the body).
- Config parsing drops blanks so an unset env cannot match an empty `stripe_price`, with a regression test.
- The meter is simple and index backed (unique key plus lookup index), and skips queries entirely for full access users and owners.
- Good coverage of month rollover, past due, grace period, incomplete, pruning, and signed link expiry.

## Test coverage
Strong: AC-1 to AC-16 each have a `covers:` test, including negative cases (invalid plan, Stripe error, past due, ended subscription, drafts, feed has no player). Stripe is faked at the HTTP client and S3 through a temporary URL builder, so there are no live calls. Gap: the oversized single block preview noted above. The accepted races (two tab extra view) are intentionally untested.
